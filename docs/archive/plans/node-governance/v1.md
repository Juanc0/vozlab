## Goal

Close the governance loop for nodes and edges: content created through the API is
born `PENDING` and today **no route moves it on** (F-01). After this plan, a node
or edge can transition `PENDING → ACTIVE` (approve) or `PENDING → REJECTED`
(reject) through the API, by its author (maintainer) or by a moderator/admin,
with an auto-apply override that reuses the existing FR-13 machinery. The
decision D-03 is settled and recorded: content is **visible on creation, marked
unreviewed**, and moves to `ACTIVE` by author or moderator action (not hidden,
not auto-accepted). The seed stops bypassing the flow. Done means: every state
in the `Node`/`Edge` transition table that this plan covers is reachable through
the API and exercised by a test, and the web inspector lets an authorised user
approve or reject the selected node/edge.

## Decision settled by this plan (D-03)

- **Visibility:** `PENDING` nodes and edges are **visible** in the graph (the
  subgraph query already includes them) but marked as *unreviewed* (dashed
  border, status badge). `REJECTED` content is excluded from the graph and from
  the Relator's neighbour list.
- **Activation:** `PENDING → ACTIVE` by (a) the object's author (maintainer,
  `author_hash` match) or (b) any `MODERATOR`/`ADMIN` of the workspace.
- **Rejection:** `PENDING → REJECTED` by the same actors.
- **Auto-apply:** `MODERATOR`/`ADMIN` may force-activate a `PENDING` node/edge
  when `community_score ≥ 10` **and** the author has been inactive for ≥ 14 days,
  reusing the criteria from `EditProposal.autoApply` (FR-13).
- **Terminal states unchanged:** `MERGED`, `DEPRECATED`, `REJECTED` remain
  terminal. `ACTIVE → MERGED | DEPRECATED` is unchanged (merge proposals).
- **No quorum in v1:** distinct-supporter quorum (G3) is deferred to Area C.
