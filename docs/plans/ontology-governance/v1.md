## Goal

Close the ontology governance gaps that block community growth (F-16): properties can
be activated and rejected (G1, G4), class rejection is exposed (G4), property keys
are unique per workspace (G7), activation requires locale completeness (G8), ontology
proposals are votable (G2), proposals auto-open a discussion thread (FR-11), and
deprecation with migration targets exists (G5, G6). A first consumer reacts to
ontology events (G9). Done means: every gap listed in §4 of
`knowledge/graph-and-ontology-strategy.md` that this plan covers is closed through
the API and exercised by a test, and the web ontology admin surface lets an
authorised user act on proposals.

## Decision settled by this plan (D-12)

- **Property activation follows the same model as class activation** (ADR-0051):
  `PROPOSED → ACTIVE` by the proposer (author) **or** any `MODERATOR`/`ADMIN`;
  `PROPOSED → REJECTED` by the same actors.
- **Locale completeness is a precondition of activation** (G8): a property or class
  must carry at least `es` and `en` display names before it can be activated.
- **Deprecation requires a migration target** (G5, G6): an `ACTIVE` class/property
  can be deprecated only when a replacement key is specified; nodes/edges using a
  deprecated key are re-typed by proposal, never by a silent script.
- **Quorum counts distinct institutional accounts** (G3): anonymous event members
  can support but cannot decide; distinct `global_user_id` (or `author_hash` for
  non-linked users) is the counting unit.
- **Proposal→thread linking is automatic** (FR-11): creating a proposal opens a
  `discussion_threads` row with `targetType = 'PROPOSAL'` and `targetId = proposal.id`.
